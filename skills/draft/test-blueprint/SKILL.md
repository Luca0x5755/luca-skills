# Test Blueprint

Analyze a project and propose its test blueprint — which layers exist, what each one tests, who fills it, and when CI runs it. Once approved, write `docs/test-blueprint.md` and crystallize the deterministic half into scripts and CI config.

The line the whole skill runs on: **judgment crystallizes into scripts.** Same input, same output, runs unattended → a script or config file, generated here. Reading a spec, weighing cost against risk, choosing policy → judgment, and every judgment in this skill ends as a proposal a human approves.

## 0. Read the existing blueprint

A `docs/test-blueprint.md` already present means revision mode: the proposal in step 3 becomes a delta against it, never a fresh document. No file means first run; [`TEMPLATE.md`](TEMPLATE.md) starts it.

## 1. Take stock

Three inventories. Sources are named, not guessed — anything missing, ask for:

- **Promises** — what the spec, stories, and scenarios commit to. Taking scenarios by dictation is normal (same discipline as `/uat-cases`).
- **Existing tests** — where current tests sit: which layer each belongs to, where and when it runs today.
- **Seams** — the module boundaries where integration bugs live. List them; the project's bug history marks the sore ones (defects cluster).

## 2. Derive the proposal

- **Layer table** — for each layer (static / unit / integration / acceptance): what it tests in *this* project, who fills it, which CI tier runs it.
- **Seam list** — the seams worth testing, each with the promise it serves. This is the list `/tdd` reads.
- **Traceability table** — promise → layer → tier. A promise with no row is a gap, and gaps go into the proposal as a **gap list** — a promise nobody can test is a finding, not a footnote.
- **CI tiers** — start from [`CI-DEFAULTS.md`](CI-DEFAULTS.md) — mandatory read. Every default is overridable per project; each override carries its reason in the proposal.

The assignments are fixed, not per-project choices: static layer → scripts and CI config generated by this skill; unit and integration → `/tdd`; acceptance → `/uat-cases` then `/browser-evidence`. Scheduling lives here in the blueprint — the downstream skills own *what*, never *when*.

## 3. Propose, then wait

Present the layer table, seam list, traceability table with its gap list, and the tier layout with every deviation from the defaults flagged. Then stop for approval. Approval is what authorizes the writes — nothing touches a file before it. Revision mode presents the delta the same way: changed rows, added and retired seams, tier moves, each with a one-line reason.

## 4. Write, then crystallize

After approval, three products:

1. `docs/test-blueprint.md` per [`TEMPLATE.md`](TEMPLATE.md).
2. Static-layer check scripts, wired to the project's own toolchain (lint, format, types) — each a hard gate: red blocks, no advisory mode.
3. CI workflow files implementing the approved tiers.

Scripts and workflow files are deterministic products of the approved blueprint — when they need to change, revise the blueprint and regenerate. A hand-edit that survives means the blueprint lies about what CI does.

Then stop. The files are the deliverable; committing them is the user's move via `/git-commit`.

## Where this sits

Downstream of `/to-spec` (promises come from it). Upstream of the executors: `/tdd` takes the seam list, `/uat-cases` → `/browser-evidence` take the acceptance assignment and their schedule. Findings from failure triage that change policy — quarantine entries, tier moves — come back through step 0 as revision proposals, never as silent edits.
